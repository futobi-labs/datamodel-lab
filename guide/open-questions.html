Open questions & ideation

The parts of modeling practice that are not settled yet, each with a short take. The takes are positions to argue with, not conclusions, and several will probably change as the platforms do.

Layers and architecture

Is silver still worth it when bronze is views?

With mirroring and shortcuts, bronze is often a set of zero-copy views over current source data. If silver is then mostly renames and casts, materializing it looks like ceremony.

Take: materialize silver when more than one consumer reads the cleaned entities, or when it does real entity work (deduplication, survivorship, the header-to-line join behind silver.sales_order_line). Leave it as views when gold is its only reader and the logic is trivial. Either way, keep the contract tests; they matter more than whether the layer is physical.

Data Vault in a lakehouse?

Data Vault (hubs, links, satellites) separates integration from presentation and handles many sources and auditability well. It also triples the table count and pushes all the dimensional work into a later layer anyway.

Take: worth it when you integrate many overlapping sources with strong audit requirements and a team that already knows the method. For a handful of sources feeding one star, a well-tested silver layer does the same integration job with far less machinery. Vault-style hash keys and insert-only satellites are worth borrowing on their own.

Modeling for the engine

One big table or a star for Direct Lake?

One big denormalized table (OBT) removes joins, which some engines love. Direct Lake transcodes per column, so an OBT means repeating every customer and product attribute on every sales row.

Take: star, still. VertiPaq is built for star joins, conformed dimensions are what make drill-across work, and repeating attributes on the fact inflates the columns that must be paged into memory. OBT is a reasonable serving shape for an ML feature table or a single-purpose export, not for a shared semantic model.

SCD Type 2 in the lake or in the warehouse?

Delta MERGE in Spark is mature, and Change Data Feed can supply the changes. Warehouse T-SQL offers multi-table transactions and is more familiar to SQL-first teams.

Take: put it wherever the rest of gold is written. The worst option is computing history in one engine and facts in another, because point-in-time lookups then span two transactional systems.

In Microsoft Fabric

Several of these questions are moving targets because the platform is. Direct Lake on OneLake, Warehouse MERGE, IDENTITY columns, OneLake security and calendar-based time intelligence all arrived or changed status during 2025. Revisit a take when its underlying feature reaches general availability.

Where semantic logic lives

Semantic model, metrics layer, or code?

Measures used to live only in the semantic model. Now semantic link lets notebooks evaluate them directly, other platforms offer metric definitions in their catalogs, and transformation tools have semantic layers of their own.

Take: for a Fabric estate, keep measure definitions in the semantic model and make other consumers call it (semantic link for notebooks, XMLA or Excel for analysts) rather than re-deriving Net Sales in Python. Two definitions of a metric will diverge; the question is only when.

AI agents reading semantic models

Copilot and Fabric data agents answer questions by reading model metadata: table and column names, descriptions, synonyms, relationships and measures.

Take: this makes naming and descriptions a functional requirement, not documentation. A model with hidden keys, clear measure names and a description on every measure is noticeably easier for an agent to query correctly. The open part is how much modeling should bend toward agents (fewer, broader measures; explicit verified answers) versus toward human report authors.

Open question

If agents become a primary consumer, does the semantic model need its own test suite of natural-language questions with expected answers, in the way gold has contract tests? Probably, and nobody has a standard shape for it yet.

Beyond BI

Modeling for BI and ML at the same time

BI wants conformed, slowly changing, human-named dimensions. Machine learning wants point-in-time-correct, wide, per-entity feature rows with no leakage from the future.

Take: they share more than it seems. A Type 2 dim_customer with trustworthy valid_from and valid_to is exactly what a point-in-time feature join needs. Build feature tables as a serving layer on top of gold, reusing its keys and history, rather than as a parallel pipeline from bronze.

Rule of thumb

When a question here comes up on a real project, write down the deciding factor you used. Over a few projects that list becomes a better guide than any of these takes.

Ideas to try

Things worth building or testing on the sample model, most of them as explorations:

  • Impact analysis. In the Column lineage tracer, pick a silver column such as silver.sales_order_line.discount_amount and see every gold column, measure and report that would break if it changed.
  • Weight lineage by what flows. The Lineage flow weights edges by column count. Try weighting by row volume or refresh time instead, and see which tables dominate.
  • Toggle the inactive relationship. In the Star schema explorer, switch the active date role from order to ship date and see which measures change meaning.
  • Grain lint. In the Medallion stack, flag any gold column that does not hold one value at its table's declared grain.
  • Empty cells as questions. In the Bus matrix, click an empty cell (Inventory by Customer) and explain why it is empty, rather than leaving users to discover it.
  • Animate a cold query. In the Engine layer cake, compare a cold Direct Lake query after framing with a warm one.
  • Model diffs from Git. Semantic models saved as TMDL are plain text. A visual diff of relationships and measures between two commits would make model reviews far easier.
  • Contract cards. Generate a one-page contract (grain, keys, tests, freshness) for each silver and gold table from metadata, and link it from every exploration node.
