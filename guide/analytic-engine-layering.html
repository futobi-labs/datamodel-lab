Analytic engine layering

A report visual is a query that falls through five layers before it touches a file. Knowing which layer does the work explains most performance problems, and most of the design rules elsewhere in this guide.

The useful habit is to ask "which layer is slow?" before asking "how do I make it faster?" A cold Direct Lake query is a storage and transcoding question. A slow measure on a warm model is a query engine question. A report page that fires forty queries is a consumption question.

Storage: OneLake, Delta and V-Order

OneLake stores every Lakehouse and Warehouse table as Delta Parquet, and shortcuts let one copy appear in many items. Because every engine reads the same files, file layout is a shared concern: small files and tiny row groups slow down Spark, the SQL engines and Direct Lake alike.

V-Order is a write-time optimization that applies special sorting, row group distribution, dictionary encoding and compression to Parquet files. The files remain standard Parquet, so any reader can use them, but VertiPaq and the Fabric SQL engines read them faster. It costs some write time.

  • Warehouse writes V-Ordered files by default.
  • Spark's default depends on workspace settings and runtime version. Newer workspaces may default to a write-optimized configuration with V-Order off, so check rather than assume.
  • Turn it on for gold tables that Direct Lake reads. Bronze rarely needs it.
-- Spark SQL: enable V-Order on a gold table and compact it
ALTER TABLE gold.fact_sales SET TBLPROPERTIES ('delta.parquet.vorder.enabled' = 'true');
OPTIMIZE gold.fact_sales VORDER;

Property and configuration names have shifted between Fabric Spark runtime versions; confirm them against the current documentation for your runtime.

Compute: who writes what

  • Data Pipelines orchestrate and copy. They are the natural home for metadata-driven loops and on-premises extraction through a gateway.
  • Dataflows Gen2 run Power Query at scale and can write to Lakehouse or Warehouse. Good for low-code shaping; less good for complex, versioned logic.
  • Spark notebooks write Lakehouse Delta tables: bronze landing, silver cleansing, Delta MERGE.
  • Warehouse runs distributed T-SQL with full DML and multi-table transactions, which suits dimension and fact loads that must commit together.
  • The SQL analytics endpoint gives every Lakehouse a read-only T-SQL surface: views, functions and SQL security, but no writes to tables.
Watch out

The SQL analytics endpoint picks up Spark writes through a metadata sync that can lag. A pipeline that writes with Spark and immediately reads through the endpoint may see the previous state. If a step depends on fresh data through the endpoint, trigger or wait for the sync explicitly.

The semantic engine: Direct Lake, Import, DirectQuery

All three modes put the same VertiPaq engine in front of the user. They differ in where column data comes from.

Framing is how a Direct Lake model "refreshes": a metadata operation that points the model at a specific Delta table version. It takes seconds, copies no data, and is the moment new rows become visible. Transcoding is what happens on query: columns the query needs are loaded on demand from Parquet into VertiPaq's in-memory format. The first query after framing pays that cost (a cold cache); later queries run at Import-like speed until columns are evicted under memory pressure.

Direct Lake now comes in two flavors. Direct Lake on the SQL analytics endpoint can fall back to DirectQuery through the endpoint when it meets something it cannot read directly: a SQL view, SQL-level security, or a table that exceeds the capacity's guardrails. The model's DirectLakeBehavior setting controls whether fallback is allowed. Direct Lake on OneLake reads Delta tables straight from OneLake, does not fall back (queries that exceed limits fail instead), cannot use SQL views, and can combine tables from more than one Fabric item. Check the current status of each flavor and their guardrails for your capacity size.

Direct Lake rewards gold tables that are V-Ordered, compacted and narrow. Row groups map to VertiPaq segments, so a table written as thousands of tiny files will be slow to transcode and may hit file or row group guardrails. Schedule OPTIMIZE on gold, frame the model after the load completes, and consider warming the cache with a few representative queries before users arrive.

Query: formula engine and storage engine

Every DAX query is split between two engines. The storage engine scans compressed columns, applies simple filters and aggregates, runs multi-threaded and caches its results. Its requests are expressed in an internal language called xmSQL. The formula engine handles everything else: complex filter context, iteration, branching logic. It is single-threaded and works on the data caches the storage engine hands back.

Fast measures push work into the storage engine. Slow measures force callbacks, where the storage engine has to ask the formula engine to evaluate an expression row by row (an IF inside a SUMX over a large table is the classic). In DirectQuery, storage engine requests become SQL sent to the source instead of xmSQL scans. Performance Analyzer and DAX Studio's server timings show the split.

-- Roughly what the storage engine runs for Net Sales by Category in 2026 (xmSQL, simplified)
SELECT 'Product'[Category], SUM ( 'Sales'[Net Amount] )
FROM 'Sales'
  LEFT OUTER JOIN 'Product' ON 'Sales'[Product Key] = 'Product'[Product Key]
  LEFT OUTER JOIN 'Date'    ON 'Sales'[Order Date Key] = 'Date'[Date Key]
WHERE 'Date'[Year] = 2026;

How one visual query travels down the stack

Take a bar chart of Net Sales by Category, filtered to 2026, on the "Sales Overview" report.

  1. Consumption. The visual generates a DAX query against the "Sales & Inventory" model.
  2. Query. The formula engine resolves Net Sales to SUM ( Sales[Net Amount] ) and the year filter to a filter on Date, then asks the storage engine for one data cache.
  3. Semantic engine. The storage engine needs Sales[Net Amount], Sales[Product Key], Sales[Order Date Key], Product[Category] and Date[Year]. Any column not already in memory is transcoded.
  4. Storage. Transcoding reads those columns from the Parquet files of the framed version of gold.fact_sales, gold.dim_product and gold.dim_date in OneLake. V-Order and healthy row groups make this fast.
  5. Back up. The scan returns a few rows (one per category), the formula engine assembles the result, and the visual renders.
EVALUATE
SUMMARIZECOLUMNS (
    'Product'[Category],
    TREATAS ( { 2026 }, 'Date'[Year] ),
    "Net Sales", [Net Sales]
)

A notebook can take the same path. Semantic link evaluates the measure through the same engine, so the number matches the report exactly:

import sempy.fabric as fabric

df = fabric.evaluate_measure(
    "Sales & Inventory",
    measure="Net Sales",
    groupby_columns=["Product[Category]"],
)
Rule of thumb

Fix performance at the lowest layer that causes it. Do not rewrite DAX to compensate for small files, and do not compact tables to compensate for a measure full of callbacks.
