Conformed dimensions & the bus matrix

A conformed dimension is a promise that "Product" means the same thing everywhere it appears. That promise is what lets sales, inventory and budget sit on one page and agree with each other.

What conformed means

Two facts share a conformed dimension when they use the same keys, the same attribute names and the same attribute values. "Same values" is the part that fails in practice: if the budget file says Outdoor Gear and the product master says Outdoor, the dimension is not conformed, no matter how tidy the tables look.

Conformance comes in two strengths:

  • Identical. Both facts join to the same physical table on the same key. fact_sales and fact_inventory_daily both use dim_product.product_key and dim_warehouse.warehouse_key.
  • Shrunken. One fact uses a strict subset of the dimension: fewer rows (a rollup level) or fewer columns. Every value in the shrunken version exists in the base version, with the same spelling and meaning.

Facts can be conformed too. If "net amount" appears in sales and in a returns fact, it must be calculated the same way (gross less discount, same currency, same tax treatment) or carry a different name.

Rule of thumb

Derive every shrunken dimension from its base dimension, never from the fact that needs it. dim_product_category is SELECT DISTINCT category FROM dim_product, and budget rows are validated against it, not the other way round.

Shrunken and rollup dimensions

fact_budget is set at month x product category x region. It cannot join to dim_product on product_key, because no budget exists at product level, and it cannot join to dim_date on a day. There are three ways to handle it:

ApproachHowTrade-off
Shrunken dimension tablesBuild dim_product_category and a month-level date table in gold; relate budget to themClean one-to-many relationships, but the model gains tables, and users must know which Category to use
Relate at the coarser attributeIn the semantic model, relate Budget to Product on category and to Date at month (many-to-many, single direction)One Product and one Date table for everything, but measures must guard against filters below the budget grain
Allocate downSpread category budget to products by last year's mixFake precision. Only do it when the business has agreed the allocation rule.

The sample model takes the second approach in the semantic layer, while still validating budget categories against dim_product in gold. The rule above holds either way: the category list is owned by the product dimension, and silver.budget maps the budget file onto it, flagging anything that does not match.

With a many-to-many relationship on category, a filter on a single product still propagates to its category's budget, which silently shows the whole category's budget against one product's sales. Guard the measure:

Budget =
IF (
    ISFILTERED ( 'Product'[Product Name] ) || ISFILTERED ( 'Date'[Date] ),
    BLANK (),
    SUM ( Budget[Budget Amount] )
)

Budget Variance = [Net Sales] - [Budget]

ISFILTERED reacts to slicers as well as visual rows, which is usually what you want for a plan measure. If you only want to blank it on rows below the grain, use ISINSCOPE instead.

The bus matrix for the sample model

The enterprise bus matrix is a planning tool disguised as a table. Rows are business processes (facts); columns are conformed dimensions. Each filled cell is a commitment that the fact will use that dimension, at the grain noted.

Read down a column to see the dimension's reach: Product touches all three facts, so it is the dimension to get right first. Read across a row to see a process's scope. Empty cells are information too: inventory has no customer, so a report that slices inventory by customer is asking an impossible question, and the model should make that visible rather than silently repeat totals.

Region in the budget is a rollup of the customer's sales region in the sample. If budgets were set by warehouse region instead, the cell would move to the Warehouse column, and that decision is exactly the conversation the matrix is meant to provoke before anyone builds tables.

Rule of thumb

Draw the matrix before the first fact table, then deliver row by row. Each new row should mostly reuse existing columns; a row that needs three new dimensions is a new domain and deserves a design review.

Drill-across

Drill-across means answering one question from two facts, such as "net sales against closing inventory by category and month." The rule: aggregate each fact separately to the shared, conformed grain, then join the results. Never join two facts row to row; the fan-out multiplies both sides.

WITH sales AS (
    SELECT p.category, d.year_month, SUM(f.net_amount) AS net_sales
    FROM gold.fact_sales AS f
    JOIN gold.dim_product AS p ON p.product_key = f.product_key
    JOIN gold.dim_date    AS d ON d.date_key    = f.order_date_key
    GROUP BY p.category, d.year_month
),
stock AS (
    SELECT p.category, d.year_month, SUM(f.on_hand_qty) AS closing_on_hand
    FROM gold.fact_inventory_daily AS f
    JOIN gold.dim_product AS p ON p.product_key = f.product_key
    JOIN gold.dim_date    AS d ON d.date_key    = f.date_key
    WHERE d.is_month_end = 1
    GROUP BY p.category, d.year_month
)
SELECT COALESCE(s.category, i.category)     AS category,
       COALESCE(s.year_month, i.year_month) AS year_month,
       s.net_sales,
       i.closing_on_hand
FROM sales AS s
FULL OUTER JOIN stock AS i
  ON i.category = s.category AND i.year_month = s.year_month;

In a semantic model, drill-across is the default behavior and the real payoff of conformance. Put Product[Category] and Date[Year Month] on a matrix with Net Sales, On Hand Units and Budget, and the engine evaluates each measure against its own fact through the shared dimension tables. No join is written, and no fan-out is possible, as long as the dimensions are truly shared.

Governance: keeping conformed dimensions conformed

Conformance decays unless someone owns it. The practical minimum:

  • One owner and one load per conformed dimension. Other teams consume it; they do not rebuild it with their own filters.
  • Domain tests on every load. Every category in silver.budget exists in dim_product; every region exists in dim_customer; no fact carries a key the dimension lacks.
  • Change control on attribute domains. Renaming a category is a business decision with downstream effects on budgets, targets and saved report filters. Treat the value list as a governed artifact.
  • Documented attribute definitions. "Region" needs one definition, written where both modelers and report authors will find it.
In Microsoft Fabric

Keep conformed dimensions in one gold Lakehouse or Warehouse and let other workspaces reach them through OneLake shortcuts rather than copies. Direct Lake models in different domains can then read the same Delta tables. Endorse (promote or certify) the shared semantic model so report authors build thin reports on it instead of importing their own Product table. Fabric domains help group workspaces by business area, but they do not enforce conformance; tests do.

Open question

In a data mesh, each domain owns its data products. Who owns Customer when sales, service and finance all describe customers? One answer is a small central team that owns only the conformed dimensions and the bus matrix, with domains owning their facts. Whether that scales past a handful of domains is still being argued.
