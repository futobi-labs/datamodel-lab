Semantic engine

On the left, the inside of a semantic model: tables, relationships with their cardinality and filter direction, hierarchies, and measures that lean on one another. On the right, the engine that answers it. Pick a visual and a storage mode, run the query and watch the formula engine plan, the storage engine scan, columns page into memory and the timings add up.

Two engines, one query

Every DAX query is answered by two engines working as a pair. The formula engine is single-threaded and clever: it understands filter context, time intelligence and iterators, and it does arithmetic on small intermediate results. The storage engine is multi-threaded and simple: it scans compressed columns, applies filters and joins along relationships, and returns grouped aggregates called datacaches. Fast models push as much work as possible into the storage engine, in as few scans as possible. Measures that force the formula engine to iterate row by row, like the semi-additive On Hand Units here, are where time goes.

Where the columns come from

Direct LakeColumns are read straight from Delta Parquet files in OneLake the first time a query touches them (transcoding), then stay in memory. A load followed by a reframe points the model at the new files and the next query pays the paging cost again. No copy, no scheduled import.
ImportColumns were copied into memory at the last refresh. Queries never leave VertiPaq, so they are the fastest and the most predictable, at the cost of a scheduled refresh and a second copy of the data.
DirectQueryThere is no VertiPaq data. Each storage engine request becomes SQL sent to the warehouse, so every scan costs a round trip. Direct Lake on the SQL endpoint falls back to this when it cannot read the files directly, for example when SQL-level security applies.

What the numbers are

The timings are illustrative, not measured: they come from a simple cost model (scan size, joins, paging and round trips) so the shape is right even if the milliseconds are not yours. To see real ones, run the same visual's query in DAX Studio with Server Timings on, or use Performance Analyzer in Power BI Desktop. The structure is real: the measures, relationships and hierarchies all come from the shared sample model, and the query plan is derived from them.
